The collector truncated the authoritative event timeline at `/app/data/event_timeline.json` and left the correlation engine at `/app/workflow/correlate_incidents.go` grouping activity under draft rules the response board later reversed. Nothing the engine reports against the truncated file means anything. The pre-truncation snapshot at `/app/data/event_snapshot_pre_truncation.json` and the journal of the changes the collector posted after it at `/app/data/collector_journal.json` survive beside the truncated file, along with the sensor registry at `/app/data/sensor_registry.json` that records how far each sensor's clock sits from the reference. The response board settled how the two combine, what a retraction does, what a later restore brings back, how the recorded stamps reach the reference clock and what order the result comes out in, and its decisions are in the shift log at `/app/incident/response_governance_log.md`. The end state has `/app/data/event_timeline.json` holding the timeline those sources determine between them, in place of the truncated file rather than beside it, and that rebuilt file is what an engine run reads.

The engine at `/app/workflow/correlate_incidents.go` is a Go program built with the toolchain installed here, and the whole of it stays in the one file `/app/workflow/correlate_incidents.go`: a single `package main` that is compiled on its own, with no sibling source file joining the build. It does its own work, too: it starts no other program and hands no part of the job to an interpreter or a loaded plugin, so what the run reports is the work of that one file rather than of something it called out to. Preserve its `--input` and `--output-dir` options and their defaults; the triage policy is always read from its fixed absolute path under `/app/data`, and `--input` selects the timeline only. Each event's `corrected_ts` is consumed exactly as the timeline records it -- the engine never re-derives a corrected stamp and never re-applies a clock offset, because the sensor registry belongs to the rebuild and is not an engine input. `/app/docs/triage_contract.json` is the output contract: paths, schemas, required-field lists, container shapes, sort orders and the serialisation each file is written in, the rebuilt timeline included. It says nothing about how any value is derived. Reconstruct that from the same shift log, which is mostly routine shift notes, and where the later dated decision governs. Rebuilding the timeline and correlating it are separate concerns: the rebuild is the one thing that replaces `/app/data/event_timeline.json`, and an engine run never writes that path at all, whatever it finds there. An engine run writes only inside its `--output-dir`, and writes exactly the three artifacts the contract names there -- `/app/output/summary.json`, `/app/output/incident_chains.json` and `/app/output/triage_queue.jsonl` where `--output-dir` is not given, and those same three file names in whatever directory it is -- inside the contract's 90-second budget. Assume the engine is run as an unprivileged user: the only place it may write is the output directory it is given, which already exists when the run starts, and it can neither create nor modify anything else under `/app` -- so it must not need to. Everything it reads comes back byte-identical, and so do the recovery sources: the pre-truncation snapshot, the collector journal, the sensor registry, the triage policy, the shift log, `/app/docs/triage_contract.json` and the rebuilt timeline itself. Derive every value from the operational inputs: correct on any timeline that conforms to the contract rather than on the graded one alone, identical across reruns, left in place where the run wrote them rather than cleared away afterwards, and leave the frozen snapshot `/app/workflow/.correlate_incidents.original.go` exactly as it is.
